# CPA ServiceNow Application Repository

This repository is intended to host a single ServiceNow scoped application managed through GitHub source control.

It is created from the CPA application repository template so that every new ServiceNow application repository starts with a consistent governance layer.

## Repository purpose

This repository contains two distinct layers:

1. **Governance layer**
   - Pull request standards
   - Code ownership
   - GitHub workflow stubs
   - Editor and linting standards
   - Repository documentation

2. **ServiceNow generated layer**
   - Application metadata generated by ServiceNow
   - Files committed by ServiceNow Studio, IDE, or source control integration

The ServiceNow generated layer must not be manually restructured or hand-edited outside of the approved ServiceNow development workflow.

## Important principle

This template intentionally does **not** prescribe, create, or reserve any paths for ServiceNow generated content.

ServiceNow should create and manage its own generated repository structure when the scoped application is linked and committed.

## Repository naming convention

Application repositories should use the following naming pattern:

```text
cpa-app-[domain]-[function]
```

Examples:

```text
cpa-app-client-hrsd
cpa-app-client-csm
cpa-app-client-finance
```

Use lowercase characters, hyphens between words, and avoid spaces, underscores, or special characters.

## Branching model

The expected branch model is:

```text
main
release/vX.Y
feature/[TICKET-ID]-short-description
bugfix/[TICKET-ID]-short-description
hotfix/[TICKET-ID]-short-description
```

Recommended usage:

- `main` represents production-ready code.
- `release/vX.Y` represents release candidate code for UAT or pre-production.
- `feature/*` branches are used for individual stories or changes.
- `bugfix/*` branches are used for defects.
- `hotfix/*` branches are used for urgent production fixes.

## Pull request expectations

All changes should be reviewed through pull requests.

Pull requests should include:

- Plain English summary of the change
- Linked Jira or ServiceNow ticket
- Testing evidence
- Confirmation that no hardcoded `sys_id` values have been introduced
- Confirmation that scope isolation has been considered
- Deployment or rollback notes where relevant

## Commit message standard

Use a Conventional Commits style where practical:

```text
type(scope): short description - TICKET-ID
```

Examples:

```text
feat(script-include): add retry handling - ACOE-123
fix(business-rule): prevent null reference - ACOE-456
security(acl): restrict write access - ACOE-789
chore: initial repository setup - ACOE-101
```

Suggested types:

```text
feat | fix | refactor | chore | docs | test | security
```

## ServiceNow source control guidance

- Do not mix update-set-based deployment and GitHub-based deployment for the same application.
- Do not manually edit ServiceNow generated metadata files unless this is part of an approved recovery process.
- Resolve ServiceNow metadata conflicts through the ServiceNow instance wherever possible.
- Pull the latest changes before starting work and before raising a pull request.
- Keep feature branches short-lived and focused on one logical change.

## Repository ownership

Update `.github/CODEOWNERS` before the first production use of this repository.

The default template owner should be replaced with the correct platform or application team.

## First-use checklist

After creating a repository from this template:

- [ ] Rename the repository using the approved naming convention.
- [ ] Update this README with the application name and purpose.
- [ ] Update `.github/CODEOWNERS` with the correct owning team.
- [ ] Apply branch protection rules.
- [ ] Link the ServiceNow scoped application to this repository.
- [ ] Commit the initial ServiceNow application baseline.
- [ ] Confirm the governance files remain in place after the ServiceNow commit.
- [ ] Raise and merge a test pull request to validate the repository workflow.
